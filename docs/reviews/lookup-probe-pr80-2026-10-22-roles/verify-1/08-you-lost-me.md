## Findings (location · issue · severity · suggested fix · verifiable against a source?)

1. **SKILL.md step 4a and the probe table: the claim that the answers cannot come from memory.** The answer key is a public table inside SKILL.md, which sits in the repository the probing agent can Read. A role 2 with no web access can grep the real DOI, copy its title and `created.date-time` out of the skill, and answer the made-up DOI with `NOT FOUND` without looking anything up. That passes all three answers. Reader (a) follows "Both are there so that the answers cannot come from memory" perfectly and concludes the probe cannot be faked offline. It can, from the repository itself. · **High** (the mechanism belongs to Reviewer 2; filed here because the sentence is what misleads) · Keep the answer key out of anything the prober can Read, or make the probe ask for something no file holds. At minimum, say that the key is on disk and the probe must not be able to see it. · Yes: SKILL.md holds the key, and role 2's grant includes Read and Grep.

2. **docs/index.html entry: "None of these can be answered from memory."** This is false for the made-up DOI on its own. "Not found" is the default answer for any invented identifier, so a model can give it without looking. The probe only works because the made-up DOI is paired with the real one. A visitor takes the sentence to mean each question is unguessable. · Medium · Say what is true: "Together, these cannot be answered from memory." Or drop the sentence. · Yes.

3. **docs/index.html entry: "every check still passed".** A visitor reads this as bad citations slipping through. The appendix says all twelve citations were later confirmed. What actually passed were the report gates, on a review that never resolved anything. The sentence is true and still invites the false belief that the shipped references were wrong. · Medium · "…and the review's own checks still passed, though no reference had been looked up." · Yes: appendix of doc_review_process.md.

4. **docs/index.html entry: the headline "…now stops the review".** A visitor reads "stops" as enforced. Two different things are mixed up here. The stop itself is an instruction in the skill, which the running model follows. What a tool enforces is only that a finished report saying `unavailable` fails the check. · Medium · "…now halts before any reviewer starts, and a report that says it could not look anything up fails the check." Or split it into what the skill does and what the gate refuses. · Yes: the skill text compared with the roster.sh code.

5. **docs/index.html entry: "The report must record the result".** By default a report with no `Lookup:` line still passes (process-file table: "passes, reported as undeclared"). It fails only under `--require-lookup`. A visitor takes "must" as enforced for everyone. · Low–Medium · "The report records the result…", or name the opt-in. · Yes: the `Lookup:` table and the roster.sh undeclared branch.

6. **docs/index.html entry: "the checker's own project settings blocked the web" and "the skill now asks for a little-known paper's exact title".** A checker has no project settings: they were the consumer project's settings. "Asks for a … title" leaves it unclear who is asked, and reads as if the human must supply a title. · Low · "…the project's own settings blocked the web", and "the skill now has the citation checker look up a little-known paper and return its exact title, confirm that a made-up DOI is not found, and quote a value from a web page." · Yes.

7. **Roster gate message for `unavailable`: the last two lines offer "write 'Lookup: not needed' instead".** The message never gives the condition stated in the process-file table: "never after a probe that failed". Reader (a), told their report fails and shown this escape, can follow the message exactly and relabel a failed run. · **High** · Add "only if the probe was never needed. A run whose probe failed cannot become 'not needed'." · Yes: the roster.sh message compared with the `Lookup:` table.

8. **Roster gate message for `live` with no `00-lookup-probe.md`: "Save the lookup probe's reply there, verbatim".** If the reply was not kept, the only way to obey this is to rebuild the reply from memory. Step 4b of the skill calls that worse than an admitted gap. The message never says to re-run the probe instead. · Medium · "…verbatim, if you kept it. If you did not, re-run the probe. Never reconstruct a reply." · Yes: SKILL.md step 4b.

9. **What `Lookup: live` will be taken to certify.** The process file says correctly that `live` certifies the route, not the references. But the record carries one token for both roles. A run whose route was a connector (it passes the two DOI answers and fails the web-page answer) on a papers-only deliverable writes `live`, exactly as a run that cleared role 6 does. A reader of the record sees `live` and assumes both roles could reach their sources. A second gap: the probe runs as role 2's agent, yet the web-page answer is said to "clear role 6". That holds only if role 6's grant equals role 2's, and the connector paragraph's instruction to add the server to rows 2 *and* 6 is the only hint. · Medium · State in the token table that `live` may cover role 2 only, and that the prose after the dash must say which roles were cleared. Say outright that the web-page answer clears role 6 only when role 6 holds the same grant as role 2. · Partly: the process file and the skill's examples.

10. **Probe question 3 and the "what each answer proves" table: "read an arbitrary web page, not only a database".** The page is `api.crossref.org/works/<DOI>`, which is the JSON record of a citation registry: a database. A Crossref connector could answer it. Reader (a) takes a pass to mean role 6 can read documentation pages, which is a different capability. · Medium · Point question 3 at a plain documentation-style HTML page with a stable value, or drop the claim to "arbitrary". · Yes.
