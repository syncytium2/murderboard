An anti-slop review process for documentsOpen source · Apache-2.0

The Murderboard

Older sense of the word: a panel convened to tear a thing apart before it goes public, hostile enough that the real hearing holds no surprises.

Executive summary

The problem. Documents go out with claims nobody checked. A number that disagrees with the analysis it came from. A reference that exists but credits the wrong paper. A total that changes between two pages. A caption claiming more than its figure shows. This happens whenever nothing sits between writing a draft and sending it — no step where someone tries to break it. People have done this for as long as they have written things down. Machines now do it faster, and in better prose.

The response. A written procedure, eleven reviewer roles that each attack the draft from a different angle, three scripts that enforce the parts people forget, and a fixed format for what comes back. It is free, tied to no particular field, and works the same whether the reviewers are people or AI.

How it works. Every sentence must either be checkable against something real — the data, the code, a source someone actually opened — or carry a visible mark saying it is not. All eleven roles run every time. The report names all eleven and says what each one found, including the ones that found nothing, because otherwise a review that ran seven of them looks exactly like a review that ran all eleven. The three rules people kept forgetting are now scripts that run on their own.

The cost. Eleven reviewers read the draft. One person decides which of their findings to act on and makes the fixes. Then the corrected document is read again, because fixes break things. A caption or a one-line summary does not get eleven reviewers — one person walks the same eleven checklists in a single pass. The effort scales down; the coverage does not.

The limits. A clean report proves the reviewers did their jobs. It does not prove the document is right. It cannot supply knowledge nobody involved has — an expert in the field will catch, half asleep, things this misses entirely. And it is unfinished on purpose: every rule here was added after something slipped through, so it covers the mistakes already made and nothing else. Expect to add to it. Caveat emptor.

Why it exists

Everything here traces to a real defect

Slop is not bad writing. It is confident writing that nobody checked. It reads as finished. Nothing on the page separates a verified sentence from a plausible one.

People have always done this. Citations copied from other citations until the original says something else. A number transcribed wrong once and repeated for a decade. A methods section describing what was meant to happen. Machines repeat these faults faster and in better grammar; the faults are the same ones. The process does not care who wrote the draft.

The common forms:

The ordinary kind

  • A statistic that disagrees with the run it claims to summarize.
  • A reference list written from memory — real-looking, partly invented.
  • A citation that checks out and still credits the wrong paper. That a source exists does not make it the source.
  • A count that contradicts itself, because two sections counted different things.
  • An identifier copied wrong.
  • A caption claiming more than its figure shows.

The subtler kind

A plotted number can match its caption exactly and still be wrong, because the code behind it misused a library or rewrote a method the project already had.

A figure is only as sound as the method behind it, so the review reads the code that made the number. Two of the eleven roles do nothing else.

An appendix to the process document records the incident behind each rule. None were invented.

The core principle

One rule underneath the rest

Every sentence must be either verifiable against a real source — the data, the code, a prior result, a checked citation — or explicitly flagged as unverified.

No unsourced claim. No invented citation. No contradiction. No filler. What cannot be verified is neither deleted nor quietly kept: it ships marked ⚠, so the reader can see which sentences carry weight.

The process

Draft, attack, repair, re-attack, deliver

Six steps, numbered because the order matters. Step 0 runs before the draft exists. Step 4 rereads the repaired document; it is the step people skip, and it catches the fixes that broke something else.

  1. 00

    Preflight — is the process itself current?

    Your copy of the process drifts behind the original. Review against a stale copy and you skip rules you already paid for. A script checks this — see the gates.

  2. 01

    Draft the document

    Write it as you always would. The point is that this draft is not what you deliver.

  3. 02

    Review — run the whole panel

    Every role runs, every time. What changes with the stakes is how you run them, not which. A long document gets eleven reviewers. A one-line caption gets one person walking all eleven checklists. A role that finds nothing says so, and says what it checked: silence and absence must not look alike.

  4. 03

    Synthesize and apply

    Collect the findings, drop the duplicates, rank them, and decide each one: fix it, flag it, or reject it with a reason. Then make the fixes.

  5. 04

    Verify the fixes — a fresh pass on the repaired artifact

    Reread the corrected document, ideally with someone who did not review the draft. Three questions. Is each finding truly fixed, not merely claimed fixed? Was anything quietly dropped? Did a fix break something else? The third is common: a fix that lengthens a caption pushes it onto the figure. If a script builds the document, rebuild it and check the rebuilt file — the generator is not the deliverable. Build last, not fix last.

  6. 05

    Deliver with a receipt

    The corrected document, a plain-language summary, and a role ledger — one row per role, all of them. See what you hand over.

The review team

Eleven seats on the panel

Each role gets the draft and the real sources — data paths, code, companion documents — and returns findings in one shape: location, issue, severity, suggested fix, and whether it could be checked against a source.

Anyone building their own version tends to divide the roles wrongly, so here is the reasoning.

01

“Prove It”

Claim & data verifier

Pulls every factual and numerical claim and checks each against the data, the code, or the earlier result. Returns a table: quoted value, cited source, recomputed value, match or mismatch. Recompute. Never eyeball.

02

“DOI or Die”

Citation & reference validator

Confirms each reference exists and says what is quoted. Then the half that gets skipped: is it the origin, or merely the earliest source the reviewer reached? Follow the cited work's own references back until they stop, and report where you stopped. A shared author is not a shared laboratory.

No guessed bibliographic detail, ever. This role also never folds into a self-review, however short the document: one pass inherits the writer's search history and stops where it stopped.

03

“Cross-Examiner”

Consistency auditor

Checks counts, totals, terms, and whether the figures and the text agree — within the document and against its companions. Watches for one group counted two ways, which is how the same “N” changes between slides without anyone noticing.

04

“Reviewer 2”

Adversarial reviewer

Reads as a hostile peer reviewer: overreach, unsupported leaps, missing caveats, undefined quantities. Asks the question that kills a soft result — could it ever have come out otherwise?

05

“Kill Your Darlings”

Line editor

Clarity and precision. Undefined jargon, ambiguity, redundancy, flow. Every sentence must earn its place and assert exactly one true thing.

06

“RTFM”

Methods / domain expert

When the document rests on a method, model, or library, this role reads the source paper and the documentation before reviewing. Never reason from memory about what a function does.

07

“Reinventing the Wheel”

Reuse auditor

Catches new code redoing what the project already does in tested production code — and, where it does redo it, whether it matches: same parameters, orientation, unit conversions, guard clauses.

08

“You Lost Me”

Naive-reader accessibility

Reads with no prior knowledge and marks every place a cold reader is lost. A document can be right in every number, honest, and cleanly made, and still be unreadable to the people it was written for.

09

“Show, Don't Tell”

Density & figure-first

Asks what no other role asks: what here should have been a picture? Drafts default to prose — correct, complete, sourced, and unreadable at a glance.

10

“Ship It”

Build & craft gate

Owns every check settled by opening the rendered file or running a script: overlaps, unlabeled axes, clipped text. It answers in a table, not prose, so a skipped check leaves a visible hole.

11

“Start With the Problem”

Argument order

Reads only the order. A deck can be true, readable, and clean on every slide and still fail, because it gives the fix before the reader knows there is a problem.

Why the roles divide this way. Two reasons, both learned the hard way.

What it costs to answer. You can satisfy a judgment call (“would a cold reader follow this?”) by thinking. You can satisfy a mechanical check (“is this axis labeled?”) only by opening the file. Give one reviewer both, and its prose answer covers for the file it never opened. So every mechanical check sits alone, in seat 10.

What gets read at once. Most roles read one slide at a time. A fault that belongs to the whole sequence, or to the whole page, is invisible to all of them: each slide passes on its own. Seats 9 and 11 read at those larger sizes, so the reader is not the one who finds them.

The gates

A rule that depends on being remembered is not a gate

Three of these rules were prose for years, and each was skipped exactly when it mattered. Each is now a script that runs by itself and stays quiet when the answer is fine. Take this part even if you take nothing else. It works on any rule you cannot afford to leave to memory.

Where the roster gate came from. “Every role runs” was prose. Then a run using 7 of 11 roles and a run using all 11 produced reports no reader could tell apart. “No findings from role 9” is worth nothing if role 9 never ran. So the ledger became required, and then machine-checked.

Every gate ships --selftest, which proves each branch can still fire. An alarm that cannot ring is not an alarm.

The output contract

Three things, or it isn't finished

1 · The corrected document

Not the draft plus a list of its faults. The repaired document — and if a script builds it, the rebuilt file, newer than the last fix and newer than everything it draws on.

2 · A plain-language summary

What was checked, what was found and fixed, how many rounds it took, and every ⚠ still standing. Plus the warning below.

3 · The role ledger

One row per role, all of them, each carrying its findings or its “no findings, and here is what I checked” line. This is the only evidence the panel ran. If nothing survived review, say so. Never invent findings to look thorough.

Read this before you quote a run

What it does not do

A clean run is evidence the roles ran. It is not evidence the artifact is correct. The process requires you to say so, in the delivered summary, in these terms or equivalent:

“This review found and fixed N defects. It is not a correctness proof. The convergence table measures how quickly reviewers stopped finding things, not whether anything remains.”

The run record is the most quotable thing the process produces, and “11/11 roles, severity floor reached” reads to anyone as a clean bill of health. The role ledger fixed one confusion: “7 of 11” and “11 of 11” look alike. It did not fix the next one. “11 of 11 and clean” and “11 of 11 and correct” also look alike, and the second is what a reader takes away. No table can tell a document with nothing left to find from one whose reviewers all looked in the same wrong place.

It does not replace an expert

The panel checks that claims are sourced, consistent, traced to their origin, and legible. It cannot supply judgment nobody involved has. Someone who knows the field will catch, half asleep, what this process misses at full effort: that a result is implausible for reasons no source states, that the method is sound but wrong for the question, that the interesting finding is the one nobody wrote down.

Run it as a floor under expert review, never as a substitute.

It is not finished, and is not meant to be

Every rule here was added after something slipped through. That is the only evidence a rule is worth having. It also means the set is incomplete: it covers the mistakes already made and says nothing about the next one.

So it is built to change. The roster is read from the process file rather than remembered, and the freshness gate exists because copies go stale in silence. Expect to add to it.

Caveat emptor. Adopt it as a discipline that raises the floor and leaves a record. Do not adopt it as a guarantee. Do not let a clean report stand in for someone competent having read the thing.

Implementation

Putting it in your own project

Nothing to install and nothing to subscribe to. Each project keeps its own copy of the files, so a fresh download works on any machine. Copies go out of date in silence, which is why the freshness gate exists.

Six words the rest of this section uses

repo
Short for repository: the folder of files that is your project, tracked by version control (almost always git) so every change has a history.
vendor (verb)
To copy someone else's files into your own project rather than depend on them remotely. You get a project that works offline forever; you take on the job of updating the copy.
stamp
A one-line note added to each copied file recording exactly which version it came from. Without it, "is my copy old?" is unanswerable.
hook
A script your tools run automatically at a fixed moment — when a session starts, before a commit. This is how a check stops depending on anyone remembering it.
exit code
The number a script returns when it finishes. 0 means fine; each other number means something specific. It is how one script's verdict can drive another's behaviour.
gate
A check placed so that work cannot proceed past it unnoticed. The opposite of a written rule you are trusted to recall.

  1. Copy the files in, and stamp them

    The process document under docs/, the scripts under tools/, and — if you use Claude Code — the skill to .claude/skills/murderboard/. Each copy carries a one-line stamp naming the commit it came from, so drift shows. Use the repo's murderboard_revendor.py; editing the stamp by hand corrupts files.

  2. Wire the gates so they fire without being remembered

    Freshness at session start, as an early warning. The roster check against every finished report. This step is what makes it a process rather than a good intention.

    # session start — silent unless your copy is stale
bash tools/murderboard_freshness.sh --hook

# after a review run — exit 1 if a role left no trace
bash tools/murderboard_roster.sh check REPORT.md

  3. Point the literature tool at your library

    Reviewers need real papers, not remembered ones. fetch_paper.py fetches only from open-access hosts, keeps what it gets, searches your own library before downloading, and adds anything paywalled to a list for a human rather than scraping it. It needs Python 3, plus pypdf or pdftotext to read PDFs.

    export MURDERBOARD_LIT="/path/to/your/pdf/library"

python3 tools/fetch_paper.py --have smith attention   # check the library first
python3 tools/fetch_paper.py <url>                       # fetch, cache, print text
python3 tools/fetch_paper.py --need "<citation>"          # flag one you can't reach

  4. Make it the default, in writing

    Add a rule to your project's instructions — CLAUDE.md, a contributing guide, a team norm — that documents go through the murderboard before delivery. The repo ships a paragraph to paste. Skip this and the files sit unused. The first three steps make the rule enforceable; this one makes it a rule.

If you use Claude Code

Install the skill and run /murderboard <artifact>. It runs the parts that must not depend on memory: it checks freshness at the moment of review rather than at startup, reads the roster from the process file, resolves the document to the built file rather than its generator, fingerprints it before and after, and writes a record the roster gate then checks.

If you don't

None of this requires AI. The eleven roles are a checklist; the gates are shell scripts. Run the panel as human review — one person in eleven passes, or eleven people in one — and hand back the same three things. The structure and the record do the work, not the reviewer's identity.
