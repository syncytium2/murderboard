An anti-slop review process for documentsOpen source · Apache-2.0

The Murderboard

Older sense of the word: a panel convened to tear a thing apart before it goes public, hostile enough that the real hearing holds no surprises.

Executive summary

The problem. Documents go out with claims nobody checked. A number that disagrees with the analysis it came from. A reference that exists but credits the wrong paper. A total that changes between two pages. A caption claiming more than its figure shows. This happens whenever nothing sits between writing a draft and sending it — no step where someone tries to break it. People have done this for as long as they have written things down. Machines now do it faster, and in better prose.

The response. A written procedure, eleven reviewer roles that each attack the draft from a different angle, three scripts that enforce the parts people forget, and a fixed format for what comes back. It is free, tied to no particular field, and works the same whether the reviewers are people or AI.

How it works. Every sentence must either be checkable against something real — the data, the code, a source someone actually opened — or carry a visible mark saying it is not. All eleven roles run every time. The report names all eleven and says what each one found, including the ones that found nothing, because otherwise a review that ran seven of them looks exactly like a review that ran all eleven. The three rules people kept forgetting are now scripts that run on their own.

The cost. Eleven reviewers read the draft. One person decides which of their findings to act on and makes the fixes. Then the corrected document is read again, because fixes break things. A caption or a one-line summary does not get eleven reviewers — one person walks the same eleven checklists in a single pass. The effort scales down; the coverage does not.

The limits. A clean report proves the reviewers did their jobs. It does not prove the document is right. It cannot supply knowledge nobody involved has — an expert in the field will catch, half asleep, things this misses entirely. And it is unfinished on purpose: every rule here was added after something slipped through, so it covers the mistakes already made and nothing else. Expect to add to it. Caveat emptor.

Why it exists

Everything here traces to a real defect

Slop is not bad writing. It is confident writing that nobody checked. It reads as finished, which is the whole difficulty — nothing on the page separates a verified sentence from a plausible one.

It is not a machine phenomenon. Every failure below has a long human pedigree: citations copied from other citations until the original says something else, numbers transcribed once and propagated forever, methods sections describing what was intended rather than what was run. Language models reproduce these faults at higher throughput and with better grammar, which changes the economics of skipping review, not the nature of the defect. The process is indifferent to who drafted.

The recurring shapes:

The ordinary kind

  • A statistic that disagrees with the run it claims to summarize.
  • A reference list written from memory — real-looking, partly invented.
  • A citation that resolves perfectly and still credits the wrong paper. Existence is not origin, and only one of the two usually gets checked.
  • A count that contradicts itself between sections, because two sections counted on different bases.
  • An identifier copied wrong.
  • A caption that overclaims what its figure actually shows.

The subtler kind

A plotted number can be perfectly consistent with its caption and still be wrong, because the code that produced it misused a library or re-derived a method the project already implements correctly.

A figure is only as sound as the method behind it. So the review reaches past the prose into the analysis code that generated the number — two of the eleven roles exist for exactly that.

The process document keeps an appendix recording the specific incident behind each rule. None are hypothetical, and none were invented to round out a list.

The core principle

One rule underneath all of it

Every sentence must be either verifiable against a real source — the data, the code, a prior result, a checked citation — or explicitly flagged as unverified.

No unsourced factual or quantitative claim ships unflagged. No fabricated or approximate citation. No internal contradiction. No filler. Anything that cannot be verified is not deleted and not quietly kept — it ships carrying a visible ⚠ so the reader knows which sentences are load-bearing and which are not.

The process · a real sequence

Draft, attack, repair, re-attack, deliver

Six steps. They are numbered because the order is load-bearing: step 0 runs before the draft exists, and step 4 — re-reviewing the repaired artifact — is the one that is skipped in practice and the one that catches fixes which broke something else.

  1. 00

    Preflight — is the process itself current?

    The process file gets copied into your repo, where it quietly drifts behind the original. A review run against a stale copy silently omits rules you already paid for. This is a script, not a reminder — see the gates below.

  2. 01

    Draft the document

    Normally. Nothing special happens here — the point is that this draft is not the deliverable.

  3. 02

    Review — run the whole panel

    Every role runs on every deliverable. What scales to the stakes is how you run them, never which ones. A big document gets eleven parallel reviewers; a one-line caption gets a single pass that still walks all eleven checklists. A role with nothing to check reports “no findings, and here is what I checked” — silence and absence must not look alike.

  4. 03

    Synthesize and apply

    Consolidate the findings, dedupe them, rank by severity, and decide each one: fix it, flag it inline, or reject it with a reason. Then actually apply the fixes.

  5. 04

    Verify the fixes — a fresh pass on the repaired artifact

    Re-check the corrected document, ideally with a reviewer who did not do the original pass. Three questions: is every finding actually resolved in the artifact rather than merely claimed; was anything quietly dropped; and did a fix introduce a new defect? That last one is common — a fix that lengthens a caption pushes it onto the figure. If a script builds the document, the deliverable is the built file, not the generator: rebuild, then check the rebuild. The last action before delivery is the build, not the fix.

  6. 05

    Deliver with a receipt

    The corrected document, a plain-language summary, and a role ledger — one row per role, all of them. See what you hand over.

The review team

Eleven seats on the panel

Each role receives the draft and pointers to the real sources — data paths, code, companion documents — and returns findings in a fixed shape: location, issue, severity, suggested fix, and whether it could be verified against a source.

How the roles are divided is the part most often got wrong by anyone building their own version, and it is worth stating explicitly.

01

“Prove It”

Claim & data verifier

Extracts every factual and quantitative claim and checks each against the actual data, code, or prior result. Returns a claim ledger — quoted value, cited source, recomputed value, match or mismatch. Recompute, never eyeball.

02

“DOI or Die”

Citation & reference validator

Confirms every reference exists and says what is quoted — then does the half that gets skipped: is it the origin, or just the earliest source the reviewer happened to reach? Open the cited work's own references and follow them back until they stop, then report where you stopped. A shared author is not a shared laboratory.

Zero tolerance for guessed bibliographic metadata. This is also the one role that never collapses into a self-review, however short the document — a single pass inherits the drafter's search history and stops in the same place.

03

“Cross-Examiner”

Consistency auditor

Cross-checks counts, totals, terminology and figure↔text agreement, inside the document and against its companions. Watches for one population counted on different bases, which is how the same “N” silently changes between slides.

04

“Reviewer 2”

Adversarial reviewer

Reads as a hostile peer reviewer. Attacks overreach, unsupported leaps, missing caveats, and undefined quantities — and asks the question that kills soft results: could this null result ever have come out otherwise?

05

“Kill Your Darlings”

Line editor

Clarity and precision. Undefined jargon, ambiguity, redundancy, flow. Every sentence must earn its place and assert exactly one true thing.

06

“RTFM”

Methods / domain expert

When the document rests on a specific method, model or library, this role reads the source paper and the actual API docs before reviewing. No reasoning from memory about what a function does.

07

“Reinventing the Wheel”

Reuse auditor

Catches new analysis code re-implementing something the project already does in tested production code — and, where it does re-implement, whether it matches the reference exactly: same parameters, orientation, unit conversions, guard clauses.

08

“You Lost Me”

Naive-reader accessibility

Reads with zero prior context and flags every place a cold reader is lost. It exists because a document can be every-number-correct, honest and craft-clean, and still be unreadable to the audience it was written for.

09

“Show, Don't Tell”

Density & figure-first

Asks the one question no other role is empowered to ask: what here should have been a picture? Generated documents default to prose — correct, complete, sourced, and unreadable at a glance.

10

“Ship It”

Build & craft gate

Owns every check whose answer is decided by opening the rendered file or running a script — overlaps, unlabeled axes, clipped text. Its output is a table, not prose, so a skipped check leaves a visible hole.

11

“Start With the Problem”

Argument order

Reads only the order. A deck can be true, readable and clean on every single slide and still fail because it presents the fix before the reader knows there is a problem.

Why the roles are cut this way. Two axes, both learned the hard way.

Cost. A judgment call (“would a cold reader follow this?”) can be satisfied by thinking about it. A mechanical check (“is this axis labeled?”) can only be satisfied by opening the file. Bundle the two into one reviewer and its prose answer covers for the file it never opened — so every mechanical check lives alone in seat 10.

Unit of analysis. Most roles read one slide or panel at a time. A defect whose unit is the whole sequence (argument order) or the whole page (how much canvas the figure was given) is invisible to all of them, because each slide passes on its own. Seats 9 and 11 exist so those defects have somewhere to be found other than by the reader.

The gates

A rule that depends on being remembered is not a gate

Three of this process's rules were prose for their whole lives, and each was skipped precisely when it mattered. Each is now a script with an exit code, wired to run automatically and silent when the answer is fine. This is the transferable part: the mechanism works on any rule you cannot afford to have depend on recall.

Where the roster gate came from. “Every role runs” was prose for its whole life. Then a run that fired 7 of 11 roles and a run that fired all 11 cleanly produced reports no reader could tell apart. “No findings from role 9” is worth nothing if role 9 was never spawned — so the ledger became mandatory, and then machine-checked.

Every gate also ships --selftest, which proves each branch can still fire. A gate that cannot ring is not a gate either.

The output contract

Three things, or it isn't finished

1 · The corrected document

Not the draft plus a list of what's wrong with it. The repaired artifact — and where it is generated by a script, the rebuilt file, newer than the last fix and newer than every input it embeds.

2 · A plain-language summary

Which dimensions were checked, what was found and fixed, how many verify rounds it took, and every remaining ⚠ flag. Plus the calibration line — see below.

3 · The role ledger

One row per role, all of them, each carrying its findings or its “no findings, and here is what I checked” line. This is the only evidence the panel ran. If nothing survived review, say so plainly — never manufacture findings to look thorough.

Read this before you quote a run

What it does not do

A clean run is evidence the roles ran. It is not evidence the artifact is correct. The process requires you to say so, in the delivered summary, in these terms or equivalent:

“This review found and fixed N defects. It is not a correctness proof. The convergence table measures how quickly reviewers stopped finding things, not whether anything remains.”

The reason is that the run record is the most quotable thing the process emits, and “11/11 roles, severity floor reached” reads to any human as a clean bill of health. The role ledger fixed “7 of 11” and “11 of 11” look alike. It did not fix the next one up: “11 of 11 and clean” and “11 of 11 and correct” look alike — and the second is what a reader takes away. No convergence table can tell a document with nothing left to find from one whose reviewers were all looking in the same wrong place.

It does not replace an expert

The panel checks that claims are sourced, consistent, attributed to their origin, and legible. It cannot supply judgment that is not in the room. Someone who knows the field will catch, half asleep, things this process will not catch at full effort — that a result is implausible for reasons no source states, that the method is sound but wrong for the question, that the interesting finding is the one nobody wrote down.

Run it as a floor under expert review, never as a substitute for it.

It is not finished, and is not meant to be

Every rule here was added after a defect got through. That is the only evidence any of them is worth having, and it also means the rule set is incomplete by construction: it covers the failures already suffered, and says nothing about the next one.

So it is built to keep changing — the roster is derived rather than recalled, and the freshness gate exists because copies of an evolving process go stale silently. Expect to amend it. A version of this that stopped changing would be a version that stopped learning.

Caveat emptor. Adopt it as a discipline that raises the floor and leaves a checkable trace, which is what it demonstrably does. Do not adopt it as a guarantee, and do not let a clean report stand in for someone competent having actually read the thing.

Implementation

Putting it in your own project

There is no package to install and nothing to subscribe to. Each project keeps its own copy of the files, so a fresh download of that project works on any machine with nothing else fetched. The cost of copies is that they go out of date silently — which is the whole reason the freshness gate exists.

Six words the rest of this section uses

repo
Short for repository — the folder of files that is your project, tracked by version control (almost always git) so every change has a history.
vendor (verb)
To copy someone else's files into your own project rather than depend on them remotely. You get a project that works offline forever; you take on the job of updating the copy.
stamp
A one-line note added to each copied file recording exactly which version it came from. Without it, "is my copy old?" is unanswerable.
hook
A script your tools run automatically at a fixed moment — when a session starts, before a commit. This is how a check stops depending on anyone remembering it.
exit code
The number a script returns when it finishes. 0 conventionally means fine; anything else means something specific and non-fine. It is what lets one script's verdict drive another's behaviour.
gate
A check placed so that work cannot proceed past it unnoticed. The opposite of a written rule you are trusted to recall.

  1. Copy the files in, and stamp them

    The process document under docs/, the scripts under tools/, and — if you use Claude Code — the skill to .claude/skills/murderboard/. Each copy carries a one-line stamp saying which upstream commit it came from, so drift is visible. Use the repo's murderboard_revendor.py rather than hand-editing the stamp.

  2. Wire the gates so they fire without being remembered

    Freshness at session start as an early warning, and the roster check against every finished report. This is the step that makes it a process instead of a good intention.

    # session start — silent unless your copy is stale
bash tools/murderboard_freshness.sh --hook

# after a review run — exit 1 if a role left no trace
bash tools/murderboard_roster.sh check REPORT.md

  3. Point the literature tool at your library

    Reviewers need real papers, not remembered ones. fetch_paper.py fetches only from open-access hosts, caches what it gets, searches your curated library before downloading, and adds anything paywalled to a want-list for a human instead of scraping it. It needs nothing beyond Python 3, plus pypdf or pdftotext if you want text out of PDFs.

    export MURDERBOARD_LIT="/path/to/your/pdf/library"

python3 tools/fetch_paper.py --have smith attention   # check the library first
python3 tools/fetch_paper.py <url>                       # fetch, cache, print text
python3 tools/fetch_paper.py --need "<citation>"          # flag one you can't reach

  4. Make it the default, in writing

    Add a rule to your project's instructions — CLAUDE.md, a contributing guide, a team norm — that document deliverables go through the murderboard before delivery. The repo ships a paragraph to paste. Skip this step and the files sit in the repository unused; the preceding three steps are what make the rule enforceable, this one is what makes it a rule.

If you use Claude Code

Install the skill and run /murderboard <artifact>. It sequences the parts that must not depend on memory: freshness gated at the moment of review rather than at startup, the roster derived rather than recalled, the artifact resolved to the built file rather than its generator and fingerprinted before and after, and a run record emitted and then checked by the roster gate.

If you don't

None of this requires AI. The eleven roles are a checklist; the gates are shell scripts. Run the panel as human review — one person in eleven passes, or eleven people in one — under the same output contract. The structure and the resulting record are what do the work, not the identity of the reviewer.
